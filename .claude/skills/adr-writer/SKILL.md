## 목적

대화 중에 내려진 아키텍처/기술 결정을 나중에 돌아볼 수 있도록 ADR 형식으로 문서화한다.
좋은 ADR은 결정 자체보다 **왜 그 결정을 내렸는지**와 **무엇을 포기했는지**를 담는다.

## 절차

### 1. 대화 컨텍스트에서 결정 추출

현재 대화를 처음부터 돌아보며 다음을 파악한다:

- **무엇을 결정했는가**: 채택한 기술, 패턴, 접근 방식
- **왜 결정이 필요했는가**: 해결하려는 문제, 현재 코드의 구체적 상황 (파일명, 설정값, 의존성 등 코드 기반 근거 포함)
- **포기한 대안**: 고려했지만 선택하지 않은 옵션과 그 이유
- **결과**: 이 결정으로 얻는 것과 잃는 것 (긍정/부정 모두)

### 2. 다음 ADR 번호 결정

```bash
ls docs/adr/*.md 2>/dev/null | sort | tail -1
```

`docs/adr/` 에 파일이 없으면 001부터 시작한다.
가장 최근 파일의 번호에 1을 더해 3자리로 패딩한다 (예: 001, 002, 003).

### 3. ADR 파일 생성

템플릿 파일 `.claude/skills/adr-writer/assets/adr-template.md`를 읽어 사용한다.
각 플레이스홀더를 치환한다:

- `{{NUMBER}}` → 3자리 번호 (예: 001)
- `{{TITLE}}` → 결정의 핵심을 담은 한 줄 제목 (동사로 시작, 예: "통합 테스트 환경으로 Testcontainers 도입")
- `{{DATE}}` → 오늘 날짜 (YYYY-MM-DD)
- `{{CONTEXT}}` → 결정이 필요했던 이유, 현재 코드의 구체적 상황 (일반론이 아닌 이 프로젝트의 실제 파일/설정 기반)
- `{{DECISION}}` → 채택한 결정과 구현 방향 (코드 예시 포함 가능)
- `{{ALTERNATIVES}}` → 마크다운 표 행 형식: `| 대안명 | 기각 이유 |`
- `{{POSITIVE_CONSEQUENCES}}` → 긍정적 결과 (불릿 목록)
- `{{NEGATIVE_CONSEQUENCES}}` → 부정적 결과/트레이드오프 (불릿 목록)

파일 저장 경로: `docs/adr/{{NUMBER}}-{{slug}}.md`
- `{{slug}}` 는 제목을 소문자 하이픈 형식으로 변환 (예: `testcontainers-for-integration-test`)
- `docs/adr/` 디렉토리가 없으면 생성한다

### 4. 완료 후

생성된 파일 경로를 사용자에게 알리고,
ADR에서 가장 핵심적인 "왜"를 한 문장으로 요약해 전달한다.

## 작성 원칙

- **맥락(Context)은 구체적으로**: 일반론("테스트가 없다")보다 실제 코드 근거("application.properties에 datasource 설정 없음 → H2 자동 구성")를 우선한다
- **대안은 실제로 고려한 것만**: 고려하지 않은 대안을 억지로 채우지 않는다
- **결과의 부정적 측면도 솔직하게**: 트레이드오프를 숨기면 ADR의 가치가 없다
- **제목은 결정의 본질을 담게**: "DB 선택" 보다 "통합 테스트 환경으로 Testcontainers 도입"처럼 구체적으로
