# ADR 002: 구현 전략을 도메인별 수직 슬라이스로 변경

- **상태**: 수락됨 (Accepted)
- **날짜**: 2026-05-09

---

## 맥락 (Context)

초기 구현 전략은 **관심사 횡단(concern-based)** 방식이었다:

```
2단계 — 모든 도메인 스타일 정리 (주석 제거, var 타입 명시, Optional 패턴)
3단계 — 모든 도메인 서비스 추출
4단계 — 트랜잭션 경계
5단계 — 누락 기능 구현
6단계 — 도메인 책임 이동
```

이 구조에서는 한 도메인이 여러 단계에 나뉘어 처리된다.
예를 들어 `CategoryController`의 스타일 정리는 2단계, `CategoryService` 추출은 3단계가 되어
Category 도메인이 한 번에 완결되지 않는다.

또한 단계가 도메인 경계를 무시하기 때문에 각 단계가 6개 도메인
(Category, Member, Product, Option, Wish, Order)에 걸쳐 있어 범위가 넓다.

---

## 결정 (Decision)

구현 전략을 **도메인별 수직 슬라이스(domain-by-domain)** 방식으로 변경한다.

```
2단계 — Category 도메인: 테스트 → 스타일 → 서비스 추출
3단계 — Member  도메인: 테스트 → 스타일 → 서비스 추출
4단계 — Product 도메인: 테스트 → 스타일 → 서비스 추출 → 검증 책임 이동
5단계 — Option  도메인: 테스트 → 스타일 → 서비스 추출 → 검증 책임 이동
6단계 — Wish    도메인: 테스트 → 스타일 → 서비스 추출
7단계 — Order   도메인: 테스트 → 스타일 → 서비스 추출 → 트랜잭션 → 누락 기능
```

각 단계에서 하나의 도메인을 완결한다. 도메인 순서는 복잡도 오름차순으로 결정했다.

각 도메인 내 작업 순서는 고정한다:

```
1. 통합 테스트 작성  →  현재 API 동작을 Green 테스트로 고정
2. 스타일 정리      →  의미 없는 주석, var 타입 명시, Optional 패턴
3. Service 추출    →  Controller는 HTTP, Service는 비즈니스
4. 도메인 개선      →  해당 도메인에만 적용되는 추가 작업
```

---

## 고려한 대안 (Alternatives Considered)

| 대안 | 기각 이유 |
|------|----------|
| 관심사 횡단 방식 (기존) | 한 도메인이 여러 단계에 나뉘어 처리됨 — 각 단계 완료 시 도메인이 불완전한 상태로 남음. 단계 하나의 범위가 넓어 테스트 실패 원인을 좁히기 어려움 |
| 전체 일괄 리팩터링 | 테스트 없이 모든 변경을 한 번에 진행 — 회귀 발생 시 원인 추적 불가 |

---

## 결과 (Consequences)

**긍정적:**
- 각 단계 완료 시 하나의 도메인이 완결 — 단계 사이에 항상 테스트 Green 상태 유지
- 회귀 범위가 좁음 — 문제가 생기면 현재 작업 중인 도메인 안에서 원인 탐색
- 단순한 도메인(Category)으로 패턴을 검증하고, 복잡한 도메인(Order)에 적용 — 학습 곡선 완만
- Order처럼 여러 관심사가 얽힌 도메인도 한 단계에서 일관되게 처리 가능

**부정적:**
- 단계 수가 6단계에서 7단계로 늘어남
- 도메인 간 의존성이 있을 때 진행 순서 결정이 복잡해질 수 있음 (예: `OrderService`는 `WishService`를 호출 → Wish가 먼저 완결되어야 함)
